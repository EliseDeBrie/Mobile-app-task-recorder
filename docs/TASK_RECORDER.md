# Replicating D365 Task Recorder for the handheld

Finance and operations apps ship with Task Recorder: it watches what you do in
the client and produces a task guide, a Word document with screenshots, and a
recording file. The WHS mobile app has no equivalent, which is the gap this tool
fills. This page records how Task Recorder works and which part of it each piece
of this tool reproduces, so the output reads like something the product made.

## How Task Recorder works

**It records controls, not sentences.** Every control in the client is
instrumented. When you use one, it tells Task Recorder the kind of action (a
button press, a value entry, a navigation), the control, and the data involved.
The sentence you read in the guide is generated afterwards from that.

**The sentence comes from an instruction label.** Task Recorder resolves the
label in three stages: an exact label the control asks for; a label named
`[control type]_[command or property]`; or a general-purpose fallback. There are
two fallbacks, and they are the shape of every generated step:

| Kind | Label ID | Template |
| --- | --- | --- |
| Command | `CommandUserAction` | `%2 the %1` |
| Property | `PropertySetValue` | `In the %1 field, enter %2` |

`%1` is the control label and `%2` is the command name for a command, or the
value for a property. So a button gives "Click the New button", and a field
gives "In the First name field, enter 'John'".

**A value can be shown three ways.** The author of a recording chooses per step:

* *Preferred value* repeats what was recorded: "In the First name field, enter 'John'."
* *Example value* asks the reader for their own data: "In the First name field, enter a value."
  Only steps that carry a value have this; a button does not.
* *User-supplied value* is the author's own words. On a step with a value it
  replaces the value; on a step without one it replaces the whole sentence.

**Structure comes from three node kinds.** Subtasks group a run of steps and can
nest. Info steps are numbered steps the author writes for actions that happen
away from the client. Hidden steps stay in the recording but are kept out of the
guide.

**Two annotations per step.** A *title* appears above the generated instruction;
a *note* appears after it, behind "Show more" during playback.

**Screenshots are an add-on.** Task Recorder itself takes no pictures. A
prerelease Chromium extension captures the client tab while you record, and the
Word export then embeds them. Screenshots can be regenerated by replaying the
recording.

**Outputs.** A task recording package (`.axtr`, a zip holding the recording XML),
a raw XML developer recording, and the Word document, which "contains the
recorded steps and any screenshots that were captured".

## What this tool reproduces

| Task Recorder | Here | Notes |
| --- | --- | --- |
| Instrumented controls report each action | The popup asks | Nothing on the handheld reports what you tapped, so the recorder asks for the action, the control and the value at the moment it detects a screen change. |
| Instruction label resolution | `instructions.py` | Same three-stage resolution and the same `%1` / `%2` arguments, with a label table that says tap and scan instead of click and type. |
| Preferred / example / user-supplied values | `--values`, and `user_text` per step | Same rules, including "a button has no example label". |
| Subtasks, info steps, hidden steps | `recording.py` | Same nesting and the same continuous numbering across subtasks. |
| Title and note annotations | Same names | Rendered above and after the step. |
| Browser extension screenshots | The screen recording | You record the screen with any tool; frames are selected per step from the video. |
| Word export | `--style task-guide` | Name, description, subtask headings, numbered steps, screenshots. |
| `.axtr` package | Not reproduced | An `.axtr` is only useful if finance and operations can import it, and a handheld recording cannot be replayed there. Recordings are JSON instead. |
| Playback, test generation, LCS libraries | Not reproduced | They depend on the client driving real controls. |

## Instruction labels used here

Command steps:

| Label ID | Template |
| --- | --- |
| `CommandUserAction` (fallback) | `%2 the %1.` |
| `Button_Tap` | `Tap %1.` |
| `MenuItem_Tap` | `Tap %1.` |
| `ListRow_Select` | `In the list, select %1.` |
| `Page_Close` | `Close %1.` |
| `Page_Back` | `Tap the back arrow to leave %1.` |

Property steps:

| Label ID | Template |
| --- | --- |
| `PropertySetValue` (fallback) | `In the %1 field, enter %2.` |
| `Field_Value` | `In the %1 field, enter %2.` |
| `Field_Value_Example` | `In the %1 field, enter a value.` |
| `ScanField_Value` | `In the %1 field, scan %2.` |
| `ScanField_Value_Example` | `In the %1 field, scan the value from the label.` |
| `Checkbox_Value` | `%2 %1.` |
| `Checkbox_Value_Example` | `Select or clear the %1 field.` |

A checkbox renders its value as Select or Clear rather than True or False, which
is the improvement Microsoft's own documentation uses as its worked example.

To change the wording for every step of a kind, edit `INSTRUCTION_LABELS` in
`instructions.py`. To change one step, set `instruction_label` on it, either to a
label ID or to a template of your own such as `"Press %1 twice."`.
